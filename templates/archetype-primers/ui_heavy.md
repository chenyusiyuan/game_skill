# ui_heavy interaction prototype

OpenGame 五原型之一：UI driven / no physics。它不是“卡牌/文字/经营”品类枚举，而是判断游戏主要是否由面板、按钮、卡片、对话、选择和状态机推进。

## 选择条件

- 几乎没有实时物理或自由移动；主要交互是点击、选择、拖拽、提交、翻页或购买。
- 游戏进展来自 UI 状态变化：卡牌、对话、问答、经营、放置、菜单、合成、升级、剧情分支。
- 画面可以有动画和角色，但核心输入仍是 UI 决策而不是角色移动。
- Card game、visual novel、quiz、idle clicker、management sim、shop game 都可能落到这个原型。

关键问题：玩家主要是不是在操作 UI 面板和状态，而不是操控物理对象？如果是，优先按 `ui_heavy` 处理。

## Phase A 设计重点

- `coreLoop.primaryAction` 写成阅读/选择/点击/购买/出牌 -> 状态变化 -> 反馈 -> 下一次决策。
- `uiSurfaces.primary` 是主舞台：卡牌区、对话框、按钮组、资源栏、任务栏、库存或棋盘式 UI。
- `uiSurfaces.secondary` 写清暂停、规则、结算、详情、升级、商店或历史记录。
- `visualIdentity.palette` 必须让按钮、可选项、禁用项、危险/成功状态和 HUD 清楚区分。
- 桌面标准画布为 960×720；信息密度高的经营/卡牌可以用 1280×720；极简问答可用 800×600 并说明取舍。

## Phase B 落地提醒

- 所有按钮和卡片要有 hover/pressed/disabled/selected 反馈，不能只有静态文字。
- 状态机要清楚：当前阶段、可用操作、资源变化、失败原因、下一步提示都要可见。
- 文本不能溢出按钮或卡片；信息多时用分区、列表、标签页或详情面板。
- 如果有多轮/多章节/多天经营，前 3 段必须有内容或规则变化，不只是数字递增。
- 暂停时保留当前选择和资源状态，恢复后不重置本轮决策。

## Smoke 建议

- 用短点击链证明主闭环：点击按钮、选择卡片、提交答案、购买升级、推进对话或完成一轮结算。
- state evidence 应证明状态变化：`turn >= 1`、`selectedCard != null`、`coinsChanged == true`、`dialogueIndex > 0`。
- 不要把完整剧情、多局胜利、随机抽牌理想结果或长经营循环当成 Stage 1 硬 smoke。

## 常见失败形态

- 按钮看不出可点，点击后没有状态反馈。
- 文本太多、字号太小或溢出容器，用户无法读完核心信息。
- 只有静态菜单，没有真正的回合、资源、选择或反馈。
- 成功/失败状态只在内部变量变化，画面和 HUD 不更新。
- 把 UI 面板做成装饰卡片堆叠，实际工作流不清楚。
